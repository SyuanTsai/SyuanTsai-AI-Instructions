# Skill 更新與範圍維護準則

## 文件定位

本文件供新增、修改與審查 Skill 的維護者使用，目標是讓每次更新改善具體任務，同時維持清楚的能力邊界與最少必要內容。適用於 Skill source 與 Web Consumer 的維護。

本文件保存在開發文件層。各專案的開發入口（例如 CONTRIBUTING 或 README 的維護段落）只需連結同一份已審閱版本，於修改或 Review Skill 時讀取。不要把本文複製進 SKILL.md、references、安裝包或每次使用 Skill 都載入的提示詞。尚未取得本文時，維護工作應明說缺少依據；一般 Skill 使用不依賴本文。

技能的用途、輸入、輸出及必要操作限制仍由各自的 SKILL.md 說明。本文件規範如何維護它們，不另建立一份平行的技能規格。

## 每次更新先界定問題

在既有工單或 PR 簡短交代三件事：使用者要完成什麼、目前哪個具體行為不足、這次改動到哪裡即可完成。可直接引用已有需求或重現案例，不重寫完整計畫，也不新增固定表單或機器可讀的變更憑證。

優先修正既有步驟、合併重複內容、補足必要案例，再評估是否需要新檔案、新腳本或新依賴。若現有工具與簡短說明已足以完成任務，可以不增加程式。

一般修正以既有能力邊界為準。增加新的使用者能力、外部服務、支援平台、持久狀態或自動化責任時，先將它列為明確的範圍決策；已有使用者授權就依其範圍執行，缺少授權才詢問。未採用的構想留在 backlog，不預先放入交付內容。

## 新增內容的必要性

每項新增內容都應能回答「它在什麼任務中，改善哪個決策或行為？」

| 類型 | 保留或新增的依據 | 適當位置 |
| --- | --- | --- |
| 核心說明 | 影響觸發、輸入、必要流程、輸出或錯誤處理 | SKILL.md |
| 詳細參考 | 特定操作確實需要的格式、限制或範例，且有清楚的讀取時機 | references 或必要執行資料 |
| PowerShell | 反覆使用或值得固定執行的操作；有實際入口或呼叫者，並能說明輸入與輸出 | Skill 的 scripts |
| 測試 | 驗證保留功能、錯誤處理或具體保護條件 | 開發 repository 的 tests |
| 套件資料 | 實際 discovery、資料解析、來源識別或授權需要 | 對應 metadata、schema 或授權檔 |
| 開發與交付紀錄 | 實作理由、審查結果、掃描報告、試跑與版本交接 | 工單、PR 或開發證據儲存位置 |
| 共用驗證工具 | 多專案共用的執行環境、工具取得、掃描與報告能力 | 既有共用工具；source repo 僅保留必要接入 |

references 必須有實際用途，不能用來收藏所有背景知識，或只是把過長 SKILL.md 搬到另一個檔案。維持一處主要說明，其餘用精確連結；通用常識、重複教學及不影響操作的歷史可以省略。

必要 schema、範例與授權資料可以保留，不以副檔名篩掉功能所需資源。Web Consumer 則依實際平台能力描述操作；本地 PS builder 可以留在開發 repository，不能宣稱 Web 能執行它。

## Web 採被動更新

主 Skill 是功能與說明的唯一維護來源。對應主 Skill 完成必要驗證、正常來源交付及版本定案後，Web 即可依該版本被動同步；其他來源、中央整批更新與 USER 部署不作為 Web 啟動前置。投影需要的來源版本與選取資料由已交付主 Skill 的不可變身分取得，只有實際缺少的接入資料才列為具體缺口。Web 不提前另做一套功能設計、內容精簡或來源分叉，也不作為主 Skill 或中央整合的前置條件。

Web 更新只處理來源差異、平台必要轉換、連結與資源完整性，以及適用的載入驗證。平台無法支援的能力應明確標示，不能靜默改寫主 Skill 語意。發現來源缺陷時回報來源維護單，不在 Web 複製修正；只有該 Web 交付暫停，不因此重開已完成的來源驗收。未選取或不適用的 Web 項目保留有依據的 no-change 結論，不為同步建立新能力。

## 控制依賴與責任

Skill 的執行依賴由使用者功能決定。開發整理工具、CI、掃描器需要的 Node、Python 或其他 runtime，不因此成為 Skill 使用者的安裝前置。可選工具應保持可選，不能改成每次使用時自動下載的隱藏依賴。

新增依賴前，說明既有 PS、平台工具或現有函式為何不足，以及依賴對安裝、相容性和維護的實際影響。不要為了形式一致，把既有通用框架改寫成 PS，或為單一案例新增完整 resolver、狀態機、排程、簽署、報告或驗證平台。

同一通用責任優先使用既有共用實作。移除 source repository 的副本前，確認替代入口、版本相容性與實際呼叫均可運作；缺少共用能力時提出具體缺口，不能先刪掉必要功能或把風險藏在包裝層。

授權、憑證、路徑、資料完整性、衝突、回讀及恢復等保護，依實際功能保留。個別失敗應以最小可泛化的修正處理，不把每次事故累積成所有操作必須通過的新流程。一般文件操作只要求適用的文件證據；描述程式現況時才需要對應版本與正確性證據。

## 變更與清理一起完成

改變流程或移除依賴時，同步處理受影響的舊說明、失效連結、未使用腳本、初始化、fixtures 與測試。刪除前檢查用途、直接與間接呼叫者，以及仍支援的相容情境；不能只依檔名、檔案大小或單次文字搜尋判定無用。

仍有使用者或有效呼叫者的能力，應維持功能或明確處理遷移。若涉及舊資料、mapping、plan 或 approval，相容性變更須有適用的版本與恢復處置，不能靜默沿用失效資料，也不能把刪除功能說成純整理。

有效需求與必要操作知識提取完成後，工單專屬計畫、試跑日誌及產生式報告退出 Skill 交付內容。保留可追溯歷史與原始 finding，不掃蕩其他任務的工作區、未提交變更或證據。將無用檔案移到新的 references 子目錄不算完成清理。

## Review 與完成條件

Review 以實際 diff 回答以下問題；在既有 PR 中簡短記錄即可：

- 改動是否解決已界定的需求？新增的能力與依賴是否在授權範圍內？
- 每個新增檔案、規則與腳本是否有用途與使用時機？是否已有可重用的說明或實作？
- 被替換的舊內容與依賴是否一併處理？保留功能、必要保護及相容性是否成立？
- 測試是否驗證可觀察行為，而非只比對文字、檔案數或固定程式形狀？
- 安裝內容是否只含執行所需資源？開發工具、測試與交付紀錄是否留在適當層次？

對應行為、必要回歸及 repository 已適用的正常檢查通過後即可完成本次範圍；本文件不新增獨立 CI gate、掃描器、簽核角色或例行全量重跑。未變版本的有效證據可重用並說明涵蓋範圍，未通過或未執行的項目仍如實記錄。

驗證範圍須能對應實際差異與風險。歷史文件清理檢查用途、引用與交付內容；Skill 說明變更審查語意、必要停止條件與適用掃描；PowerShell 變更驗證受影響行為與必要回歸。先區分分支必要檢查、適用規則與維護者自行追加的檢查，不把每種變更都綁到整套本機工具重建。可由正常 CI 提供同一候選的必要證據時，不另加「本機全量通過才可建立 PR」的重複前置；若既有強制要求確實過寬，應以正常變更修正其適用範圍，不跳過檢查或將失敗標為通過。

工具環境問題應在共用入口修正，避免各 Skill 加入一套補救程式。Windows 暫存路徑應在耗時準備前檢查最深子路徑所需空間，使用短且互不干擾的工作根目錄；診斷與記錄不能反過來阻擋主要操作。保留首次失敗，只在修正了具體原因後重試，不以重複下載、延長逾時或新增包裝取代根因處理。

中央驗證框架的自身測試由中央開發流程負責；Skill repository 保留功能測試與必要接入驗證。移轉責任時先確認可用替代、相容契約及原保護的驗收，再移除副本。工具取得時核對來源、版本與依賴完整性；執行時只重驗實際相關依賴，重複全量掃描須有具體風險依據。可寫目錄不能因有 receipt 或唯讀屬性就當成不可變；減少檢查必須證明必要的防修改、替換與注入保護仍成立。

共同框架的設計邊界應先於受影響規劃確定；實作與接軌只阻擋實際依賴它的交付步驟。不受影響的 Skill 功能與 Web 被動同步繼續，既有完成證據保留，新框架採用另行追蹤。

字數、檔案數與依賴數可用來發現異常成長，但沒有固定配額，也不是成果本身。內容增長應有具體需求與必要性；沒有新增內容的修正、合併或刪除，同樣可以是完整交付。

## 本準則的維護

只有反覆出現、可泛化且能改善維護判斷的問題，才值得修改本文。優先修正文意或合併既有原則；工單細節和一次性例外留在原工單。保持一份可版本追溯的文件，避免再產生各 Skill、平台或任務各自複製的規範。
