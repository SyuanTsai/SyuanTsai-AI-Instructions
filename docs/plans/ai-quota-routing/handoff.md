開始前先完整閱讀 [discussion-record.md](./discussion-record.md)，並以該文件的「已確認決策」為準。不要因新對話缺少先前聊天內容而重新推翻已確認決策；若發現衝突，應指出衝突並向使用者確認。

## 必須保留的已確認決策

1. 任務歸屬使用平台無關的 Git Repository 來源資訊判定為 task profile，不綁定 GitHub 或任何特定 Git 供應商。
2. 每個 AI 額度來源分別定義額度歸屬與可支援的 task profile；任務只能使用明確宣告支援它的來源。
3. 個人額度來源可以支援個人與公司任務；公司額度來源可以支援公司任務，但不得支援個人任務。
4. 無法確認任務歸屬時，不得自行選用未明確支援的額度來源；remote 的解析、匹配與衝突處理尚未決定。
5. 真實 Git 來源、帳號、額度歸屬、可支援 task profile 與額度資訊只能存在本機私有設定；tracked file 只保存通用規則與去識別化範例。
6. 每項額度的重置時間可能不同；需要為子任務選擇其他合格資源時，較接近重置且可能浪費的可用額度具有較高使用優先性。
7. 額度來源的支援權限先於 AI 能力與額度最佳化；後兩者不能成為使用未授權來源的理由。
8. 每個額度來源都必須具備設定預留額度的能力；同一 AI 的不同帳號或額度來源也必須各自獨立。
9. 使用者必須能依需求持續調整各項預留額度，不能只在初次設定時決定後永久固定；個人 Copilot Review 是目前已知的保障用途之一。
10. 自主路由不得侵入預留額度；其表示方式、調整介面與具體生效方式尚未決定。
11. 不在 Git Repository 中、沒有 remote 或無法判定 task profile 時，首次必須詢問使用者，並將確認結果保存在本機私有設定，供後續相同任務來源重用。
12. 任務來源改變或來源資訊與本機紀錄衝突時，必須重新詢問，不得靜默沿用或覆寫分類；相同任務來源的識別方式與儲存格式尚未決定。
13. 多 Repository 情境以當前任務為 task profile 判定單位；輔助 Repository 不各自路由，若來源使當前任務歸屬互相衝突或無法判定，必須詢問使用者。
14. 使用者啟動對話時選定的 Codex 模型與執行模式是 Conversation 及後續正式 Task 的主控，不另外建立全域、task profile 或子任務類型的永久主要模型偏好。
15. Conversation 階段只由使用者與 Codex App 進行需求釐清、問題理解、必要上下文檢視及方向探索；此時不建立正式 Task，也不啟動其他 AI 資源路由、實作派工或派工 Plan 報告。
16. 使用者確認「這件事情要做」後才建立正式 Task；這項確認不要求使用者先決定完整架構或所有實作細節。Task Planning 由 Codex 判定 task profile 並獨立完成深入分析、架構決策、完整實作規劃及必要驗收條件，規劃確立後才進入 Task Execution。
17. 使用者選擇當前 Codex 並開始對話，代表允許其執行必要主控工作；task profile 不阻止主控消耗，而是約束正式 Task 中可被自主選用的實作及額外執行資源。
18. Codex App 作為使用者入口；當前對話模型負責理解及拆分任務、判斷由主控完成或派工、協調執行與整合結果。可安全轉交且能降低當前 Codex 預期消耗的工作應優先派工；除了 Codex 本身可用的 AI 資源外，其他 AI 資源只有使用者加入後才納入可派工範圍。
19. Codex 本身除必要主控消耗外，可用於實作或其他額外執行工作的額度也是可派工 AI 資源，並適用相同的 task profile 授權、額度與預留規則；其他 AI 資源仍須由使用者加入。
20. AI 資源以實際共享的帳號或額度來源為整體，可提供多個 AI、模型或執行模式選項；共用額度的選項共同套用預留量。同一 AI／模型因帳號或額度來源不同，可以存在於多個獨立資源中。
21. Codex 在理解及拆分任務時，自主判斷各子任務的必要能力與適合的 AI、模型及執行模式；使用者不需逐次判斷或維護完整能力對照表。
22. 能力資格只使用環境已知或 AI 資源提供的客觀資訊進行低成本不相容篩選，不得臆測模型、工具或權限，也不為每次派工額外呼叫 AI、探測或執行基準測試；資訊不足且影響安全或完成時才詢問使用者。
23. 使用者只需提供資源、授權、預留額度與可選的當次任務指示或禁止條件；Codex 在每次派工時依任務、必要能力、額度、預留與既有規則自主選擇 AI 資源、模型及執行模式。
24. task profile 仍以當前任務為單位並由拆出的子任務繼承；Worker 若未來需要存在，只視為內部實作概念，不是目前需求討論重點。
25. 主控模型仍需消耗額度來理解任務、派工及整合結果；把子任務派給其他資源不能消除這項基本消耗。
26. 派工的主要額度目標是保留當前 Codex 額度，讓 Codex 能處理更多事件的理解與分析；允許其他 AI 或整體 Token 略增，但若派工描述、驗證與返工會抵銷 Codex 額度節省，就由主控直接完成。
27. Conversation 可以先進行需求釐清、初步分析及方案探索；正式 Task 的深入分析、架構判斷與完整實作規劃由 Codex 在 Task Planning 獨立完成，規劃確立前不得把這些決策工作派給其他 AI。
28. 規劃後優先派出單一檔案且驗收清楚、大量機械性，以及介面明確的獨立實作；高度耦合、會修改相同核心檔案或需要大部分 Repository 上下文的工作由 Codex 直接完成。
29. 測試新增或修改及最終驗收由 Codex 負責。適用 TDD 時，Codex 先建立最小失敗測試，再派出可獨立驗收的 production code 實作；外部 AI 的測試回報不能取代 Codex 驗證。
30. 外部 AI 可自主決定不影響既定設計的局部實作細節；若需要改變需求、介面、資料流、架構或驗收行為，必須停止相關變更並回報 Codex 決策。
31. Codex 掌管派工、驗收與整合；驗收除了指定行為與測試，也必須檢視實作是否偏離既定架構。
32. 正常派工由 Codex 自主執行；每次派工前顯示子任務、AI 資源安全名稱、模型或模式及簡短理由，但不等待確認，也不顯示 task profile 或是否高於預留額度。
33. 派工異常或設計衝突必須立即顯示，任務完成後提供整體摘要，並保留包含派工對象、狀態、結果、異常、重新派工與驗收的完整紀錄。
34. Conversation 不產生派工通知、紀錄或 Plan 報告；進入 Task Execution 的正式任務結束時，Codex 必須提供派工 Plan 報告，使使用者能回顧從原始目標、具有實質影響的規劃修改與最終規劃，到實際派工、Codex 驗收、風險及未解決事項的完整脈絡。目前不定義報告章節、欄位、順序、詳細程度、呈現方式或檔案格式。
35. 派工通知、摘要及 Plan 報告使用 AI 資源安全名稱，不顯示真實帳號、不必要的敏感識別資訊或模型內部推理。

## 接手時不要做的事

- 不要開始修改 production code、script、hook、skill 或 installer。
- 不要建立供應商清單或假設一定使用某個 AI CLI。
- 不要把平均分配、固定比例或輪替寫成已確認的預設 AI 使用策略。
- 不要為當前對話模型之外再建立全域、task profile 或子任務類型的永久主要模型偏好。
- 不要將使用者開始 Codex 對話或進行問題探索，自動視為已建立正式 Task；Conversation 階段不得啟動其他 AI 資源路由、實作派工或派工 Plan 報告。
- 不要把 task profile 當成使用者進入 Codex 對話或允許當前 Codex 執行必要主控工作的前置條件；它約束正式 Task 中的實作及額外執行資源。
- 不要把當次任務指示解讀成可以突破 task profile 支援權限或預留額度的人工覆寫。
- 不要把同一共享額度來源下的模型或執行模式視為各自擁有獨立額度及預留量。
- 不要以所有 AI 的總 Token 最少取代保留當前 Codex 額度的主要目標；也不要只為轉移消耗而接受無法驗證或會造成大量返工的派工。
- 不要為能力資格判斷額外呼叫 AI、執行探測任務或建立複雜評分。
- 不要要求使用者逐次判斷模型能力或維護完整能力對照表。
- 不要將任務理解、問題分析、架構判斷或完整實作規劃交由外部 AI 決定。
- 不要讓外部 AI 自行修改既定需求、介面、資料流、架構或驗收行為。
- 不要只依外部 AI 的完成宣告或測試回報接受結果；Codex 必須執行最終驗證並檢查架構偏差。
- 不要要求正常派工逐次等待使用者確認，也不要在一般通知或最終報告顯示 task profile 或預留額度狀態。
- 不要只回報最終結果而省略具有實質影響的規劃修改、實際派工、異常與 Codex 驗收結果。
- 不要把額度歸屬與可支援的 task profile 合併成同一個對稱規則。
- 不要因同一任務出現多個 Repository，就預設拆分任務或分別進行 AI 路由。
- 不要將 GitHub organization 規則當成唯一方案。
- 不要提前決定 Git remote 的正規化格式、匹配優先序或 authoritative remote。
- 不要提前決定預留額度的數值、比例或設定格式。
- 不要提前決定本機任務來源紀錄的識別鍵、儲存格式或管理介面。
- 不要展開 Worker、Adapter、資料結構、通訊協定或其他內部實作細節。
- 不要將預留額度設計成初次設定後不可調整的固定值。
- 不要要求使用者把真實公司網域、repository 或帳號資訊寫入 Git。
- 不要把尚未確認的提議寫成既定需求。

## 下一步建議

下一輪先檢查目前行為規則是否已足以進入實作規劃；進入前仍須處理先前延後的問題：

- 無法可靠取得剩餘額度時的安全行為。
- 指定或已選資源不可用、派工失敗時的重試、切換、詢問與完成判定。
- 已進入正式 Task 但最終沒有實際派工時，完整派工 Plan 報告的適用範圍。

這些問題未確認前不得開始實作規劃；仍維持 Worker、Adapter、資料結構、通訊與儲存機制為非目標。
