# AI 額度自主路由：討論與決策紀錄

## 文件定位

- 狀態：高階方向已確認，進入行為規則設計；尚未進入實作規劃。
- 工作分支：`codex/plan-ai-quota-routing`。
- 用途：保存已確認的目標、限制、理由與未決問題，作為後續討論的主要依據。
- 更新原則：只有經使用者確認的內容才能列為「已確認決策」；尚未確認的內容應保留在「待討論問題」。

## 1. 問題背景

在分析問題或進行功能修改時，使用者只從 Codex App 提出任務，不希望每次都手動選擇要由哪一個 AI 執行，也不希望所有工作固定消耗同一個 AI 或帳號的額度。

這個需求的核心是由使用者啟動 Codex 對話時選定的模型與執行模式擔任主控，將當前任務拆成子任務；可安全轉交且能節省當前 Codex 額度的工作，優先從 Codex 本身其他可用選項與使用者加入的其他 AI 資源中選擇實際對象，讓 Codex 額度能保留給更多事件的理解、分析與整合。高階方向已確認，下一階段聚焦使用者可見的行為規則。

## 2. 目前目標

使用者啟動 Codex 對話時，已選定本次對話的 Codex 模型與執行模式；它是當前任務的主控，不需要再建立另一層全域或 task profile 主要模型設定。Codex 應先判定當前任務的 task profile，再拆分及協調子任務，並自主判斷哪些工作必須由主控處理、哪些可以安全轉交。只要派工可降低當前 Codex 的預期消耗，且不因傳遞、驗證或返工抵銷節省效果，就優先從合格 AI 資源中選擇實際對象；允許因此增加其他 AI 或整體 Token 的消耗。若首次無法從任務來源判定，Codex 應詢問使用者，並將確認結果保存在本機供後續相同任務來源重用。每個額度來源同時保有自己的歸屬、可支援任務範圍與可調整的預留額度。

正常情況下，使用者不需要離開 Codex App，也不需要逐次指定 AI、模型、帳號或額度來源；除了 Codex 本身可用的 AI 資源外，尚未由使用者加入的其他 AI 資源不得使用。任何未明確支援目前 task profile 或缺少子任務必要能力的選項也不得使用。

## 3. 已確認決策

### 3.1 額度歸屬與可支援任務分開定義

- 每個 AI 額度來源需要分別表達「額度屬於哪個 profile」及「允許支援哪些 task profile」，兩者不是同一個概念。
- 任務能否使用某個額度來源，取決於該來源是否明確宣告支援目前 task profile，而不是要求任務與額度具有相同歸屬。
- 個人額度來源可以支援個人與公司任務；公司額度來源可以支援公司任務，但不得支援個人任務。
- 同一 AI 的個人帳號與公司帳號是不同額度來源，各自具有獨立的歸屬、可支援任務範圍與預留額度。
- AI 資源以實際共享的帳號或額度來源為整體；同一資源可以提供多個 AI、模型或執行模式選項，但這些選項不會因此各自擁有一份獨立額度。

### 3.2 各項額度具有不同重置條件

- 不同 AI 或帳號的額度重置時間不盡相同，每項額度必須獨立看待。
- AI 使用決策需要理解不同額度的可用週期；需要為子任務選擇其他合格資源時，較接近重置且可能浪費的可用額度具有較高使用優先性。
- 派工的主要額度目標是降低當前 Codex 的消耗，讓它能處理更多事件的理解與分析；只要其他硬性邊界與任務品質成立，可以接受其他 AI 或整體 Token 略為增加。
- 平均分配、固定比例或 round-robin 不作為目前確認的預設策略。

### 3.3 以 Git Repository 來源判定任務歸屬

- 任務歸屬以 Git Repository 的來源資訊判定，不綁定 GitHub 或其他特定 Git 平台。
- 判定結果應對應 task profile，讓不同組織或客戶可在未來加入，而不需更換整體判定概念。
- 無法確認任務歸屬時，不得自行選用未明確支援的額度來源；具體 remote 解析、匹配順序與衝突處理留待行為設計階段決定。

### 3.4 真實識別資訊不得進入 Git

- 真實 Git 來源、帳號、額度歸屬、可支援 task profile 與額度資訊只能保存在本機私有設定中。
- 受版本控制的內容只能保存通用規則與去識別化範例，不得要求公開真實公司或個人識別資訊才能完成分類。
- 功能不得要求將真實公司或個人識別資訊寫入 tracked file，才能完成分類。

### 3.5 每個 AI 的額度來源都能獨立設定預留額度

- 每個 AI 都必須具備設定預留額度的能力；同一 AI 的不同帳號或額度來源也必須各自獨立。
- 使用者必須能依需求持續調整各項預留額度，不能只在初次設定時決定後永久固定。
- 這項能力不代表每個 AI 必須設定相同的預留量，也不代表目前已決定預留量的值。
- 預留額度用於保障不一定由自主路由發起、但會消耗相同額度的必要工作，例如個人 Copilot Review。
- 目標是避免自主決策耗盡這些必要工作需要的額度；自主路由不得侵入預留額度。
- 同一 AI 資源中的多個模型或執行模式若共用額度，也必須共同套用該額度來源的預留量，不能分別重複計算。
- 預留量的表示方式、大小、調整時機與人工覆寫規則留待後續討論。

### 3.6 無法判定來源時首次詢問並在本機記錄

- 不在 Git Repository 中、沒有 remote，或無法從來源資訊判定 task profile 時，Agent 應在首次遇到該任務來源時詢問使用者。
- 使用者確認 task profile 後，結果應保存在本機私有設定中；後續遇到相同任務來源時可直接重用，不需每次詢問。
- 本機紀錄不得寫入 tracked file，也不得因方便重用而把真實目錄、Repository、組織或帳號資訊提交至 Git。
- 若任務來源後來改變，或現有來源資訊與本機紀錄衝突，不得靜默沿用或覆寫分類，必須重新詢問使用者。
- 如何識別「相同任務來源」、本機紀錄的格式與管理介面，留待行為及實作設計階段決定。

### 3.7 多 Repository 情境以當前任務為主

- task profile 的判定單位是當前任務，不是任務中出現的每一個 Repository。
- 同一任務涉及多個 Repository 時，應先依當前任務的主要目的與工作歸屬判定單一 task profile，再以該 profile 篩選可用的 AI 額度來源。
- 作為參考、相依項目或輔助輸入的其他 Repository，不會自行改變當前任務的 task profile，也不需要分別進行 AI 路由。
- 若多個來源使當前任務的主要歸屬互相衝突或仍無法判定，應詢問使用者，不得由 Agent 自行選擇其中一個 profile。

### 3.8 當前 Codex 模型是主控並優先保留其額度

- 使用者啟動對話時選定的 Codex 模型與執行模式，直接成為當前任務的主控；不另外建立全域、task profile 或子任務類型的永久主要模型偏好。
- Codex 負責自主判斷哪些工作必須由主控直接完成，哪些子任務可以安全地派給其他可用 AI 資源。
- 當派工能降低當前 Codex 的預期消耗，而且派工描述、驗證與可能返工不會抵銷這項節省時，應優先派工，即使其他 AI 或整體 Token 的消耗略高。
- 若派工後預期使用的 Codex 額度不低於主控直接完成，或需要過多上下文重述與反覆整合，則由主控直接完成。
- Codex 應在理解及拆分任務時，自主判斷各子任務的必要能力，以及適合的 AI、模型與 `high`、`max` 等執行模式；使用者不需要逐次判斷，也不需要維護完整的能力對照表。
- 可派工選項必須具備完成子任務所需的必要能力；Codex 只使用目前環境已知或 AI 資源提供的客觀可用資訊，進行明確不相容條件的低成本篩選，不得臆測不存在的模型、工具或權限。
- 能力檢查不得為每次派工額外呼叫其他 AI、執行探測任務或進行基準測試；更細緻的能力評分不是目前需求。
- 使用者只需提供資源、授權、預留額度及可選的當次任務指示或禁止條件；沒有明確指示時，由 Codex 自主選擇派工資源、模型與執行模式。
- 只有客觀能力資訊不足，且會影響安全邊界或任務能否完成時，Codex 才詢問使用者。
- task profile 支援權限與預留額度仍是硬性邊界。當次任務指示不能授權未明確支援當前 task profile 的資源，也不能侵入該資源所屬額度來源的預留額度。
- 子任務有多個合格派工選項時，優先使用較接近重置、較可能因未使用而浪費的可用額度。
- 條件相近時，選擇成功率較高且切換成本較低的 AI。
- 主控模型仍需消耗額度來理解任務、派工及整合結果；把子任務派給其他資源不能消除這項基本消耗。

### 3.9 Codex App 主控可用的 AI 資源

- Codex App 是使用者入口；當前對話選定的 Codex 模型與執行模式是主控，負責理解任務、判定 task profile、拆分子任務、派工、協調執行並整合結果，並在工作不適合派出時直接完成。
- Codex 本身可使用的額度也是可派工 AI 資源，並適用相同的 task profile 授權、額度與預留規則；主控角色不代表可以略過這些限制。
- 其他 AI 資源不是系統預先建立好的固定清單；只有使用者加入後，才會納入可派工範圍。
- AI 資源以共享額度為整體，可在其下提供多個 AI、模型或執行模式選項。Codex 可以選擇不同選項，但額度與預留量仍回到其共同來源計算。
- 同一個 AI 與模型可以因帳號或額度來源不同，而同時存在於多個 AI 資源中；各資源的授權範圍、額度狀態與預留額度分別判斷。
- Codex 在每次派工時，依當前任務、task profile、必要能力、額度狀態、預留額度、當次任務指示及其他已確認使用規則，選擇實際使用的 AI 資源、模型與執行模式。
- task profile 仍以當前任務為判定單位；拆出的子任務預設繼承當前任務的 task profile，避免因拆分工作而繞過任務歸屬及額度邊界。
- Worker 若未來因內部實作需要而存在，只是實作概念，不是目前需求層級的角色或討論重點。

### 3.10 Codex 確立規劃後才派出可獨立驗收的實作

- Codex 應獨立完成任務理解、問題分析、架構判斷與完整實作規劃，以維持一致且完整的上下文；這些工作不得派給其他 AI 代為決定。
- 規劃確立後，單一檔案且驗收條件清楚的實作、大量機械性修改，以及介面明確且可分別驗收的獨立元件，應優先派給合格 AI 資源執行。
- 會修改相同核心檔案、需要反覆協調的高度耦合實作，以及必須傳遞大部分 Repository 上下文的工作，由 Codex 主控直接完成。
- 測試的新增或修改由 Codex 負責。適用 TDD 時，Codex 先依既有測試規則建立最小失敗測試，再將符合獨立驗收條件的 production code 實作派出；外部 AI 可以執行測試並回報結果，但不能取代 Codex 的最終驗證。
- 外部 AI 可以自主決定不影響既定需求、介面、資料流、架構與驗收行為的局部實作細節，例如區域命名或等價寫法。
- 外部 AI 發現既有規劃與實際程式碼衝突，或需要改變整體設計才能完成時，必須停止相關變更並回報 Codex 決策，不得自行修改已確立的設計。
- Codex 掌管派工、驗收與整合。接收結果時，除了檢查指定行為與測試，也必須檢視實作是否偏離既定架構；只有通過 Codex 驗證的結果才能納入完整任務。

### 3.11 派工通知、完整紀錄與最終 Plan 報告

- 正常且符合既定規則的派工由 Codex 自主執行，不等待使用者確認。
- 每次派工前顯示簡短通知，但通知後立即執行。通知包含子任務、AI 資源的安全名稱、模型或執行模式及簡短選擇理由；不顯示 task profile 或是否高於預留額度。
- 派工發生異常、設計衝突或無法依規劃繼續時，必須立即顯示；任務完成後再提供整體派工與驗收摘要。
- 必須保留完整派工紀錄，使 Codex 能追蹤每個子任務的派工對象、模型或模式、狀態、結果、異常、重新派工與最終驗收。
- 完整任務結束時，Codex 必須提供一份派工 Plan 報告，使使用者能回顧從原始目標、具有實質影響的規劃修改與最終規劃，到實際派工、Codex 驗收、風險及未解決事項的完整脈絡。
- 派工 Plan 報告的章節、欄位、內容順序、詳細程度、呈現方式與檔案格式目前不定義，留待後續報告行為或實作設計階段決定。
- 派工 Plan 報告整理已確認決策與可驗證的規劃變更，不揭露模型內部推理，也不顯示真實帳號或其他不必要的敏感識別資訊。

## 4. 目前概念流程

```text
使用者啟動 Codex 對話並選定模型與執行模式
→ 當前 Codex 模型成為主控
→ 當前任務及其來源資訊
→ 以 Git Repository 來源資訊或既有本機紀錄判定 task profile
→ 若仍無法判定，首次詢問使用者並將確認結果保存在本機
→ Codex 獨立完成問題分析、架構判斷與完整實作規劃
→ 需要測試時，由 Codex 先建立目標測試與驗收條件
→ Codex 將實作拆成可獨立驗收的子任務
→ Codex 自主判斷各子任務的必要能力與適合的模型及執行模式
→ Codex 判斷工作是否可安全轉交，並比較派工後的預期 Codex 消耗
→ 能節省 Codex 額度時優先派工；否則由主控直接完成
→ 每次派工時，從 Codex 本身可用資源與使用者加入的其他 AI 資源中篩選選項
→ 排除未支援該 task profile 或缺少子任務必要能力的選項
→ 依各 AI 資源實際共享的額度來源套用預留額度
→ 套用使用者對當次任務的明確指示或禁止條件
→ 依額度重置急迫性、成功率與切換成本選擇合格 AI 資源
→ 派工前顯示簡短通知並立即執行，同步保留完整派工紀錄
→ 外部 AI 依既定規劃實作；設計衝突回報 Codex
→ Codex 驗證行為、測試與架構一致性後整合結果
→ 完成後提供派工摘要與從原始目標到最終結果的派工 Plan 報告
```

這個順序只描述目前確認的高層選擇優先序與硬性邊界，不代表已決定具體設定格式、評分公式或選擇演算法。

## 5. 目前階段的非目標

- 已確認 Codex App 作為主控、Codex 本身額度屬於可用 AI 資源，以及其他 AI 資源由使用者加入後才納入派工；尚不討論 Worker、Adapter、資料結構、通訊方式或其他內部實作細節。
- 尚不決定具體支援哪些 AI 供應商、模型或帳號。
- 不另外建立全域、task profile 或子任務類型的永久主要模型偏好；當前對話模型由使用者啟動對話時決定。
- 尚不決定 AI 資源的設定格式或內部表示方式。
- 尚不建立需要使用者維護的完整能力對照表，也不設計複雜能力評分系統。
- 尚不決定額度歸屬與可支援 task profile 的實際設定格式。
- 尚不決定無法判定來源時，本機紀錄所使用的識別鍵、儲存格式或管理介面。
- 尚不定義如何取得、快取或更新剩餘額度與重置時間。
- 尚不決定預留額度使用固定值、比例、任務數量或其他表示方式。
- 尚不決定使用者透過何種介面調整預留額度，以及調整如何生效。
- 尚不採用平均分配、固定比例或輪替作為預設 AI 使用策略。
- 不以所有 AI 的總 Token 最少作為主要最佳化目標；優先保留當前 Codex 額度，但仍需維持授權、安全與任務品質。
- 尚不設計具體的 AI 選擇演算法、權重或評分公式。
- 尚不處理無法可靠取得額度時的替代判定，以及派工失敗後的重試、切換與完成邊界。
- 尚不決定派工通知、完整紀錄與最終 Plan 報告的章節、欄位、內容順序、詳細程度、UI、檔案格式或儲存機制。
- 尚不開始撰寫 production code、安裝腳本或測試。

## 6. 待討論問題

延後討論：

- 無法可靠取得剩餘額度時，Codex 應停用該資源、採用本機估算，還是詢問使用者。
- 指定或已選資源不可用、派工失敗時，Codex 的自動重試、資源切換、詢問使用者與任務完成判定邊界。
