# 計畫規則

計畫詳細度應與變更範圍、風險及不確定性相稱，只保留有助於實作或驗收的資訊，不因模板存在而補寫無關項目。

- 單一區域、低風險且作法明確的修改，可使用簡短計畫，只列目標、修改、驗證及已知風險或 Scope 邊界。
- 跨越多個區域、涉及資料遷移、安全性、公開契約或其他高風險修改時，使用下列完整格式；依任務需要重複修改項目與測試情境。
- 適用測試先行時，測試情境應描述 TDD 的 Red-Green-Refactor 順序；符合 Testing 規則的排除條件時，記錄原因與替代驗證方式。

簡短計畫格式：

```markdown
- 目標：
- 修改：
- 驗證：
- 風險／不包含：
```

完整計畫格式：

```markdown
# Plan：<功能／問題名稱>

## 1. 目標與 Scope
- 整體預期結果：
- 預計產出：<本次計畫完成後的可驗收成果摘要>
- 不包含：<不納入原因或後續處理方式；沒有時填寫「無」>

## 2. 預計修改項目

### 2.1 <修改項目名稱>
- 修改內容：
- 修改原因：
- 影響或風險：

## 3. 測試情境

### 3.1 <測試情境名稱>
- 對應修改項目：
- 測試層級：
- Given：
- When：
- Then：
- TDD：Red <先失敗的測試> → Green <最小 production code 修改> → Refactor <保持測試通過的整理>；不適用時填寫原因與替代驗證方式。
```
