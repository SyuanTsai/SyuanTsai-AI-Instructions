# Development Task Delivery

## Scope and authority

- From task start or handoff through delivery, continue implementation, validation, PR feedback handling, and progress updates within the user's authorized scope. Reuse explicit standing authorization without asking for each occurrence. A review-only request remains read-only. For material scope expansion, permission changes, or irreversible actions, first prepare reviewable work, then ask only for the missing authority. <!-- ai-invariant:development-workflow.scope-and-authority -->

## PR findings and completion

- When an implementation task has a PR, proactively read every page of review threads, review summaries, Conversation comments, and CI results. Track each finding's link, applicable commit, severity, disposition, and evidence. Check the actual disposition even when a finding is resolved, outdated, or has no inline thread. <!-- ai-invariant:development-workflow.complete-feedback-inventory -->
- Fix valid, in-scope findings and validate them under the applicable Testing rules. Proactively continue authorized branch commits, pushes, and PR replies to a verifiable outcome. Reply with the fixing commit, behavior explanation, and test or CI evidence before resolving the corresponding thread. For an invalid finding or one covered by another change, provide current code and validation reasons; leave it unresolved when reviewer judgment is required. Preserve the reason, ownership, and next step for blocked or out-of-scope items rather than hiding them with resolution. <!-- ai-invariant:development-workflow.finding-evidence-loop -->
- After each change or push, refresh findings and CI and continue repairs. After the final commit, wait for the currently required review and CI to finish, then recheck PR HEAD, the reviewed commit, every finding's disposition, and required checks. Revalidate affected evidence when HEAD changes. Green checks, a merged PR, or zero unresolved threads alone do not establish acceptance. If an omission is discovered after merge, record the gap and address it in a follow-up PR within task scope. <!-- ai-invariant:development-workflow.final-head-review -->

## Ticket progress updates

- When a task is explicitly linked to a ticket and the user has authorized task-specific or standing progress updates, proactively synchronize at start or resumption, stage completion, PR creation or update, new or cleared blockers, merge, handoff, and before ending. Use concise checkpoints containing completed work, current work, blockers, next steps, and PR, commit, or validation links. Put execution details on the corresponding child issue and meaningful overall changes on the parent. Avoid duplicate comments when nothing material has changed. <!-- ai-invariant:development-workflow.ticket-progress-sync -->
- Verify the authoritative site and issue identity first; synchronize comments and truthful workflow states within existing authorization. Reuse standing authorization instead of asking again because an older prompt says to obtain it separately. Read back every write; check for duplicates before retrying an uncertain response. If access or writing fails, state that synchronization did not occur, retain a ready-to-post checkpoint, and continue unaffected work. Do not automatically create a ticket when none is linked; prepare a draft when external write authority is absent. Closure requires the entire issue's acceptance criteria. A PR merge, focused test success, or Notion handoff does not replace formal Jira progress. <!-- ai-invariant:development-workflow.ticket-authority-and-verification -->

## Latest stable versions and reproducible validation

- At the start of each development or validation run, resolve the latest stable versions of the tools, SDKs, runtimes, test frameworks, validators, and scanners controlled by that workflow from official release sources, then obtain and actually use them. Record resolution time, official source, version, executable path, and hash or digest. Prefer task-isolated environments. Changing a version declaration, writing latest, or looking up a version while executing an older binary does not meet this requirement. <!-- ai-invariant:development-workflow.latest-stable-toolchain -->
- Freeze exact versions and source identities for the entire run, and resolve again at the next run. Local, pre-push, and CI use the same policy; reused evidence must match the candidate, tool, and environment identities. If the latest version is incompatible or unavailable, record the concrete blocker and repair it within scope rather than silently downgrading or weakening checks to claim success. Older compatibility lanes may run separately but cannot replace latest-version acceptance. <!-- ai-invariant:development-workflow.frozen-run-evidence -->
- Preserve approved source and authority commits, archive hashes, action SHAs, and installation locks. Latest-version selection does not permit floating source refs or bypassing integrity and release approval. If upgrading product dependencies, the OS, IDE, driver, or host exceeds task authorization, report the current version, latest target, gap, and required upgrade work; do not upgrade silently or claim that everything is current. Record the scope and reason when the user explicitly specifies a version or accepts an exception. <!-- ai-invariant:development-workflow.version-boundaries -->

## Handoff

- Before ending or handing off, preserve the current candidate, completed and outstanding acceptance, each finding's disposition, CI results, tool versions, and ticket synchronization outcome. Distinguish historical snapshots from current state and make unmerged changes and unresolved items directly discoverable. This workflow governs active task execution; create monitoring across turns or schedules only when the user requests it and the capability is available. <!-- ai-invariant:development-workflow.handoff-continuity -->
